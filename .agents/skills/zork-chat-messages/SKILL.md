# Chat 消息与交互

按本次范围读取：

- Chat 身份、发言、订阅、Agent 输入与工具合同：[Chat 与 Agent 工具](../../../docs/chat-tools-design.md)。
- 创建/修改 Agent、授权、登录、输入等消息卡片：[交互消息设计](../../../docs/interactive-messages-design.md)。其中已确认的消息原则适用；字段名、模块划分、实施顺序和代码盘点属于可调整的建议，不表示功能已经实现。

先追踪本次真实链路：消息产生与权威提交 → 消息传递 → core 缓存归并 → UI 投影 → 用户操作 → 业务执行与结果消息。沿用已有业务服务、消息投递和订阅，检查结构化字段是否经过历史、实时事件、Mesh、缓存和平台桥接后仍完整。

## Chat 与执行的边界

- Chat 有稳定身份，独立于内部 Agent Session/Run；创建、阅读或订阅 Chat 不隐式创建一份新的成员 Session。Agent 的持续上下文可以从多个频道接收输入。
- task 是 Chat 的称呼。目标、交付、请求验收、验收意见和后续修改通过消息表达，不据此建立 Chat 的完成/待验收/取消状态或锁定输入。停止某次运行不关闭 Chat。
- 阅读、发言、实际参与者和订阅分开。参与者来自真实作者事实；订阅控制自动接收，退订不删除历史。结果消息沿原订阅规则投递，不能因为它被渲染成卡片就绕过筛选或回灌发言者自己。
- 使用稳定消息 ID 和明确来源引用关联内容，不用正文匹配、列表相邻位置、当前窗口或可替换的 Session ID 猜测关系。作者和实际执行来源由认证上下文及服务提供，不由模型填写身份来取得权限。

## 权威源 append-only，客户端缓存可修改

权威源保存原请求和后续结果消息，不回写原请求。客户端缓存是可重建的派生数据，core 可以直接修改缓存中原消息的交互状态、结果与动作字段；保留原消息 ID、位置及请求参数。不要把源的 append-only 限制错误施加给客户端缓存，也不要把客户端归并写回源日志。

归并发生在 core 消息入库链路，不依赖卡片是否可见或页面控制器是否存活：

| 到达情况               | 应有行为                                                                   |
| ---------------------- | -------------------------------------------------------------------------- |
| 请求在缓存中，结果到达 | 按引用更新原消息缓存，发布该卡片的变化                                     |
| 结果先到，请求尚未拉到 | 持久暂存关联结果；请求到达时先合并再展示，不生成虚构请求或先闪现可确认卡片 |
| 旧请求或重复页面再到达 | 保留已归并结果，不能退回初始状态                                           |
| 多阶段、重复或迟到结果 | 按实际执行尝试与权威事件顺序归并；去重，不让旧尝试覆盖当前结果             |

- 待合并结果必须能跨重启保留。请求入库、结果归并及已消费暂存记录的清理在一致的提交边界完成；该批缓存写入与对应分页/追赶水位一起持久化，不能先推进水位再丢掉结果。
- 同步游标按原始消息流推进，独立于折叠后的显示列表。隐藏独立结果行不代表未收到该消息，不用最后一张卡片的 ID 作为追赶锚点。分页位置、源事件顺序与 UI applied version 各自使用自己的作用域。
- 优先复用连续消息分页与增量追赶。普通交互卡片不以新增“按请求 ID 回查关联消息”接口为前提；结果先到由客户端暂存处理。若新需求确有跳读等不同读取方式，再按实际合同评估，不能仅凭 append-only 推导出一套额外同步机制。
- 缓存只表达已知事实，当前能否执行仍由业务服务校验。消息回放、缓存重建、历史翻页、重新打开 UI 都不能触发或重放业务副作用。

## 交互卡片是消息的呈现

- 请求用带版本的结构化内容表达受支持的业务动作、预填参数或输入要求，并提供可读正文；卡片不携带任意 HTTP 请求或可执行脚本。后续接受、补充要求和结果消息明确引用原请求。未知版本保留内容并提供不可执行的回退展示。
- UI 提交“确认这条请求”“提交这些字段”等业务意图。core 提供默认值、校验、可用动作，负责请求、持久化、恢复和结果归并。服务端校验实际操作者、当前权限、请求是否仍有效及目标配置版本；把原请求参数放在转发 helper 后面不构成业务边界。
- 用户编辑后的参数随本次提交固定；实际执行的非敏感输入可追加为确认事实，不改原建议。实际业务结果由负责执行的服务追加，普通消息文本、按钮点击或模型声称“用户已同意”不构成可信成功或授权。
- 操作接受、实际执行、结果回写分清。复用稳定提交身份及持久回执，多端确认同一请求不能造成重复效果。结果未知时恢复原操作，不更换 ID 重做；明确的新尝试与旧尝试分开关联。
- 同一数据库内的业务效果、结果消息和回执使用同一事务或等价的可靠提交边界；跨节点或外部效果用持久回执与结果投递恢复。不能依赖“API 成功后由仍开着的窗口再发一句成功消息”。创建成功、任务已接受和任务实际运行是不同事实。

## 公共能力与业务适配

公共层维护消息关联、可靠提交、可修改缓存归并和只读卡片投影。创建/修改配置、权限、登录、输入各自提供输入合同与校验、执行/恢复和公开结果映射；复用设置页及其他入口的业务服务。具体业务可以有专用组件，不必为复用合同先造 Workflow 引擎或任意脚本表单系统。

授权和登录尤其保持以下边界：

- 卡片确认针对本次业务要求，不自动给已有授权的操作增加新的审批步骤，也不让发起请求的 Agent 获得确认者的永久权限。
- 登录入口已打开不等于登录完成。每次操作绑定实际尝试及生命周期所有者；多张卡片、取消、过期、重启与迟到回调不能串用状态。
- Chat 在授权 Mesh 范围内可被其他读者读取。密码、API key、token、OAuth verifier 等走凭据通道，不进入普通消息或 Agent 订阅；只追加可公开的结果。敏感字段处理由业务合同决定，不由模型自行改成公开。

## 验证与范围

实现客户端链路时应用 [zork-client-boundary](../zork-client-boundary/SKILL.md)；修改缓存/游标用 [zork-sync](../zork-sync/SKILL.md)，修改 core 到 UI 的增量用 [zork-client-subscriptions](../zork-client-subscriptions/SKILL.md)。按 [zork-validation](../zork-validation/SKILL.md) 选择实际受影响的检查，不因本 skill 扩大到无关发布或全仓重构。

按改动选取行为证据：

- 源请求和结果仍独立存在；客户端原卡片更新后，重开页面和重启仍显示已归并状态。
- 结果先到、重启、再拉到请求能正确合并；重复请求、重复结果和旧尝试不会回退卡片或重放操作。
- 归并与水位提交一致；结果折叠不造成反复拉取，单卡片更新只影响相关记录，多端最终收敛。
- 双端确认、操作成功后回写中断和恢复不重复产生效果；实际登录状态及敏感内容边界符合业务合同。

报告实际实现和验证范围；只调整文档/skill 时检查结构与链接，不把规则写入或静态校验通过说成业务能力已经落地。
