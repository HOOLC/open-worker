# 短邀请与连接后握手：调研结论

2026-09-07。核对当前 Zork 源码、锁定的 Synch revision `6d6283f`、iroh 1.0.3 文档及源码，并做了隔离连接实验。本次仅调研和验证，没有修改运行中的邀请协议。

## 结论

可以把未完成邀请保存在 Gateway 内存里，用短票据找到并验证接入端点，建立加密连接后再获取完整信息。现有技术栈已经支持必要的地址发现；不需要另建 Zork 云控制面。

之前把大部分字段都装进邀请，属于当前协议的选择，不是 Synch/iroh 的硬性要求。继续压缩完整 JSON 并非最有效的解决办法。

## 已确认的能力与边界

1. iroh 可以只凭 EndpointId 发起连接，配置的 address lookup 会查询 IP/relay 路由信息。EndpointId 是公钥，连接会验证对应身份。它既是查找键，也是远端身份校验依据。[iroh 1.0.3 官方说明](https://docs.rs/crate/iroh/1.0.3)
2. N0 preset 默认发布、查询 n0 提供的 PKARR/DNS 服务，并使用默认 relay。这是现成的发现基础设施；relay 本身不是短码索引服务。[N0 preset 文档](https://docs.rs/iroh/1.0.3/iroh/endpoint/presets/struct.N0.html)
3. 当前 Zork 已有独立的加密 enrollment 端点，ALPN 为 `zork/enrollment/1`。它使用 N0 preset，普通在线配置本来就具备上述能力。`exchange` 先连接，再发送/接收 JSON，因此适合承载后续元数据交换。[当前接入传输](../crates/zork-mesh/src/enrollment.rs)
4. MBA 当前 Gateway 的已核实配置：Mesh 开启、offline=false，没有自定义 relay/discovery。它正适合使用默认 EndpointId-only 引导。
5. offline 配置会关闭 relay 和 address lookup。当前 `local_discovery.rs` 只为同用户、同机器提供 loopback 地址提示，不能当作跨机器 mDNS。纯局域网离线接入需要一个直接地址提示，或另做局域网发现。[当前本机发现实现](../crates/zork-mesh/src/local_discovery.rs)
6. 如果采用私有 discovery，双方必须事先知道同一引导服务，或票据额外带上最小引导地址。不能指望在连接后才告知“这次初始连接必须用的发现服务”。但 Agent/Gateway 后续业务使用的网络设置仍可在握手后传递。

## 实验结果

探针复用当前 `Enrollment::bind/exchange/serve`，服务端是隔离的临时端点，只返回测试数据，不读取任何生产 Gateway 配置、会话或凭据。

- mini1 同机实验：清空传给客户端的全部地址提示，仅保留端点 ID；成功建立连接，约 **957 ms** 后收到回复和连接后元数据。
- 物理跨机器实验：服务端在 mini1，客户端在 MBA。只传递 `EndpointAddr { id, addrs: [] }`；客户端再次清空地址列表后发起连接。默认公共 discovery 生效，约 **1746 ms** 后成功收到回复和连接后元数据。
- 服务端启动时有一个可用 home relay。没有向接收方传递 IP 或 relay URL，也没有增加短码服务器。
- 这验证了“仅凭身份发现并连接，再交换元数据”的引导能力；没有声称全部流量被强制中继，也不代表尚未实现的新邀请授权协议已经完成验收。
- MBA 的探针临时目录已删除；未重启或替换生产 Zork。源代码和结果保存在 实验目录（本地生成的验收记录）。

## 建议的票据

默认在线模式只携带：

| 字段 | 用途 | 建议大小 |
| --- | --- | --- |
| enrollment EndpointId | 找到接入端点并验证其身份 | 32 字节 |
| 随机邀请凭据 | 查找、验证这一条短期邀请 | 16 字节 |
| 短前缀 | 区分协议版本/用途 | 约 4 字符 |

48 字节二进制用 Base64URL 编码是 64 字符，加短前缀约 **68 字符**。无需 JSON，也无需对随机字节继续压缩。

这是设计估算，尚未实现：

- 已安装 Zork 的设备：`zork mesh join <短票据>`，约 **83 字符**。
- 保留当前下载安装包装：约 **196 字符**，而非目前 MBA 实测的 593 字符。
- 离线 LAN 如果附带一个 IPv4+端口，裸地址仅多 6 字节；IPv6+端口多 18 字节，再加必要的类型标记。无需把整个网络配置带上。

EndpointId 的实际类型为 32 字节公钥，可由本机锁定版本的 `iroh-base` `PublicKey::as_bytes()` 核对。[官方 EndpointId 定义](https://docs.rs/iroh/1.0.3/iroh/type.EndpointId.html)

## 建议的状态与握手

1. 桌面请求生成邀请。Gateway 在内存表中保存随机凭据的摘要、用途、到期时间及待确认身份；凭据同时作为查找索引，省掉现在另带的邀请 ID。
2. 接收方从短票据取 EndpointId，经已有 discovery/relay 建立身份已验证的加密连接。
3. 在连接内提交邀请凭据。Gateway 验证有效期、用途及单次使用状态，再返回 Gateway 的 Synch 身份、设备名称和后续网络配置。
4. 沿用现有 Synch 身份证明；手机仍由桌面确认，确认必须绑定到具体申请身份。不能因为握手变短而提前授予管理或执行权限。
5. 正式授权写入持久成员目录，再销毁/消费邀请。重试按已经确认的身份和成员关系恢复，或保留少量完成回执。

可以移到握手后的字段：设备名称、Gateway 的业务身份、成员列表、权限说明、过期时间、业务 relay/discovery 设置。初始 enrollment 端点身份已经固定在票据里，返回的 Gateway 身份通过该加密连接建立信任关系。

可以只存内存的是“未完成邀请”。进程重启后这类邀请失效，用户重新生成即可。已授权成员、设备身份及必要的提交恢复状态仍应持久化；否则 Gateway 重启会丢失授权，或把成功但丢失回执的接入误报成失败。这些状态与临时邀请不是同一层数据。

## 为什么不是直接 6 位数字

现成 discovery 的查询键是 EndpointId，不是任意短码。仅在某一台 Gateway 内存里放 `123456 → 邀请`，远端仍不知道应该查询哪一台 Gateway。

若要“全球任意设备只输入 6 位数字”，需要额外的短码映射/会合机制，或事先限定局域网、已知网关等查找范围。映射可以扩展已有 discovery 服务，不一定另部署一套产品控制面，但确实多了一项协议与服务职责。低熵短码还要限制尝试次数。

对当前项目建议先采用“EndpointId + 随机凭据”的短票据：复用现有发现能力，将其余信息放到握手里，变化范围明确且已有跨机器实验支撑。
