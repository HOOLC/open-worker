## 1. Data root 写入模型

### 校对对话过程

agent 提问：

> 是否确认一个 data root 同一时间只由一个 zork-agent supervisor 占用，不需要多进程或多实例 active-active 写入？

用户追问：

> 什么叫 data root

agent 澄清：

> `data root` 是 zork-agent 自己保存运行数据的根目录，例如：
>
> ```text
> <data-root>/
> ├── sessions/   # 会话事件、快照
> ├── profiles/   # 模型配置
> └── 其他运行配置
> ```
>
> 它不是 agent 操作代码的 `workspace`：
>
> - `data root`：zork-agent 的内部持久数据。
> - `workspace`：某个会话读写代码、执行命令的工作目录。
>
> 我刚才的前提换成直白说法就是：
>
> > 同一份 zork-agent 会话和配置数据，是否只会由一个 zork-agent 进程写入？
>
> 不同 zork-agent 进程若各自使用不同的数据目录，不受这个限制。

用户确认：

> 是

### 已确认决策

在上述澄清后，用户对以下问题回答“是”：

> 同一份 zork-agent 会话和配置数据，是否只会由一个 zork-agent 进程写入？

## 9. 多事件批次的逻辑原子性

### 校对对话过程

agent 提议：

> 一次持久提交只写一个事件；不再把多个 JSONL 行称为一个原子批次。

agent 给出的原因：

> 普通文件无法在没有额外提交记录的情况下保证多行同时成功或同时失败，而现有单个事件已经能表达一个完整事实。

用户纠正：

> 有办法做，每个事件加个 index 和 count 就行了，压缩的时候清理，平时忽略

agent 说明：

> 对，这能实现崩溃后的逻辑原子性。我刚才说“做不到”是错的。
>
> 例如一个批次有 3 个事件：
>
> ```text
> index=0 count=3
> index=1 count=3
> index=2 count=3
> ```
>
> 如果只写完前两个就崩溃，恢复时发现数量不足 3，整个批次都不参与 fold。因为同一会话只有一个写者、批次连续写入，所以不需要额外的 commit envelope。正常 fold 忽略 `index/count`；压缩时再清理。
>
> 这一项改为：
>
> 允许一次提交包含多个事件；每个事件记录批次内的 `index` 和 `count`，恢复时不完整批次整体忽略。
>
> 是否确认？

用户确认：

> 确认

### 已确认决策

> 允许一次提交包含多个事件；每个事件记录批次内的 `index` 和 `count`，恢复时不完整批次整体忽略。

### 校对对话过程

## 18. 不给整个存储层增加内容校验

### 校对对话过程

agent 提议：

> snapshot 必须带校验 hash；hash 验证失败时不得使用该 snapshot。

agent 给出的原因：

> snapshot 即使仍是合法 JSON，内容也可能损坏，或者状态与记录的事件锚点不一致。

用户质疑：

> 一个 json，内容损坏了不就 tm 不能解析了吗？

agent 说明：

> 不一定。
>
> 例如：
>
> ```json
> {"generation":12,"consumed_through":100}
> ```
>
> 损坏成：
>
> ```json
> {"generation":13,"consumed_through":900}
> ```
>
> 仍然是合法 JSON，也能正常反序列化。字符串中某个字符变化也一样。
>
> JSON 解析只能发现语法损坏；hash 用来发现“内容变了但语法仍然合法”的情况。它不防程序本身写错，只防写入后的静默损坏。
>
> 因为 snapshot 会让恢复过程跳过之前的全部事件，我仍建议校验 hash。是否确认？

用户追问：

> 你这不是搞笑吗？给我一个内容损坏格式不损坏的构造方法

agent 说明：

> 有：单比特翻转。
>
> 原始字节：
>
> ```text
> {"x":12}
>        ^
>        2 = 0x32 = 00110010
> ```
>
> 最低位翻转后：
>
> ```text
> {"x":13}
>        ^
>        3 = 0x33 = 00110011
> ```
>
> 只改变了一个 bit，JSON 长度、结构和 UTF-8 都没变，解析器会正常得到 `13`，无法知道原值是 `12`。hash 会发生变化。
>
> 这防的是静默位错误；如果存储只考虑进程崩溃造成的残行，不考虑静默数据损坏，就不需要 hash。两种故障不能混为一谈。

用户纠正：

> 你他妈脑子里是狗屎？硬杠？snapshot 能翻转，event 就不能翻转？

agent 撤回：

> 你说得对。刚才的论证是错的，我确实在硬拗局部方案。
>
> 如果考虑静默位错误，event、批次和 segment 同样会损坏。只给 snapshot 加 hash 没有完整的正确性意义；用损坏的 event 重建也会得到错误状态。
>
> snapshot hash 这一项撤回，不写入确认文件。
>
> 正确问题应当是：是否给整个存储层统一做内容校验，而不是单独校验 snapshot。

用户决定：

> 不做

agent 请求确认以下记录：

> 不给整个存储层增加内容校验。

用户确认：

> 对

### 已确认决策

> 不给整个存储层增加内容校验。

## 21. 不做 event_id 级去重

### 校对对话过程

agent 提议：

> snapshot 不保存完整的 `seen_events` 集合。

agent 给出的原因：

> 它会为每个历史事件永久增加一项；是否见过某个事件应通过单独的查询机制判断。

用户询问：

> 这个是干啥的

agent 说明：

> `seen_events` 是当前 `SessionState` 里的事件去重集合。
>
> 每次 fold 一个事件时：
>
> 1. 检查 `event_id` 是否在 `seen_events` 中。
> 2. 已存在就忽略该事件。
> 3. 不存在就加入集合，再修改状态。
>
> 例如同一个输入事件因为“写入成功但确认丢失”而被重投，`seen_events` 用来防止输入被处理两次。[state.rs](/Users/zuozijian/Projects/HOOLC/open-worker/crates/agent/src/session/state.rs:161)
>

> - 第二位是 `SHA-256(session_id || 序号) mod 10`。
>
> 总长度固定为 16 位。

agent给出的原因：

> Verhoeff 是非线性十进制校验，能保证发现序号中的任意单数字错误和相邻数字换位；连续序号不会产生 MOD 97 那种等差校验码。
>
> SHA 校验位使相邻序号的完整两位后缀没有可利用的规律。多位错误同时通过两层校验的概率约为 `1%`。
>
> 该方案可以直接重新计算校验，无需保存随机状态；排序仍只由前 14 位决定。

agent同时明确校验码的能力边界：

> 校验码只能发现 ID 写坏，不能发现 agent 完整地选错了另一个真实 ID；后者必须由工具语义处理。

用户询问：

> 计算成本呢？

agent说明：

> Verhoeff 部分只有 14 次查表。SHA-256 使用二进制 `session_id + sequence` 并加入固定域标识后不到 56 字节，只需计算一个 SHA-256 block；不需要堆分配，只在生成和校验 ID 时计算一次。
>
> 保守按每次 `1µs` 计算，10 万个 event 约占 `0.1` 个 CPU 核。provider 的文字 delta 不生成 event，因此不会按 token 频率计算。
>
> 可以用整数 mixer 把成本降到十几个 CPU 指令，但那会把自定义算法写进永久存储协议。为节省不到 `1µs` 放弃 SHA-256 的稳定性和可审计性，不值得。

用户确认：

> 就这样吧

### 已确认决策

> `event_id` 的序号部分是固定 14 位的十进制字符串，范围从 `00000000000001` 到 `99999999999999`；不足 14 位时在左侧补 `0`。JSONL 中以字符串保存。
>
> 第 15 位是这 14 位序号的 Verhoeff 校验位；第 16 位是由 `SHA-256(session_id || 序号) mod 10` 得到的校验位。计算 SHA-256 时使用二进制 `session_id + sequence` 并加入固定域标识。`event_id` 总长度固定为 16 位。
>
> 不采用 MOD 97，也不采用随机 guard。Verhoeff 负责保证发现序号中的任意单数字错误和相邻数字换位；SHA-256 派生位用于消除相邻序号之间可供 agent 利用的校验码规律，并将一般多位错误同时通过两层校验的概率降至约 `1%`。
>
> 所有合法 ID 的序号部分宽度相同，因此完整 ID 的字符串顺序与事件序号顺序一致，后缀两位校验码不影响排序。
>
> JSONL、segment 文件名、history、SSE cursor 和 agent 工具参数必须使用完全相同的唯一标准表示。不提供省略前导零的短写形式，也不自动规范化非标准形式。

> 校验码只能发现 ID 被写坏，不能判断 agent 是否完整地选择了另一个真实 `event_id`；后者由使用该 ID 的工具语义处理。

本项补充第 87 项，完整确定自增 `event_id` 的文本编码和校验方式。

删除通知和 `ToolUnavailable` result 对已知版本表执行相同的删除状态变化，遵循第 93 项“result 与通知不重复”的规则。

### 已确认决策

用户否决：

agent 据此修正理解：工具变化通知和版本不匹配 result 不负责传递工具说明；它们只告诉 agent 哪个工具发生了变化，并提示 agent 在需要使用时自行调用 `tool.help`。

### 已确认决策

> 工具新增通知、工具版本更新通知和版本不匹配 result 都不附带该工具的初始说明或详细说明。
>
> 它们只标明发生变化的完整逻辑工具，并告诉 agent：如果当前需要使用该工具，应自行调用 `tool.help` 查询最新、正确的详细说明。工具删除通知只说明该工具已删除。

## 102. 当前 ToolRegistry 为进程级共享目录

### 校对对话过程

agent 提议：ToolRegistry 作为进程级共享的当前工具目录，所有 session 使用同一组工具版本和实现；session 只单独保存 agent 已知版本和工具 state。Registry 更新后，各 session 在自己的下一次 provider 请求前分别发现并记录通知。

agent 说明该选择不支持只给某一个 session 增删工具。

用户确认当前阶段采用该设计：

> 目前来说，对

### 已确认决策

> 当前目标设计只提供进程级共享的 ToolRegistry。所有 session 从同一 Registry 读取当前工具、版本、说明和执行实现；session 自己只持久化 agent 已知版本和该 session 的 tool state。
>
> ToolRegistry 更新时不遍历或改写全部 session。每个 session 在自己的下一次 provider 请求前比较 Registry 与已知版本，并按第 92、98、101 项持久化和发送变化通知。

当前不实现 session 独立工具集，也不为尚不存在的需求增加预留抽象。以后如果确实需要按 session 增删工具，作为新的目标变更单独设计。

## 103. 启动时按最近活动顺序有界扫描全部 session

### 校对对话过程

agent 发现当前实现启动时会列出并 fold 全部 session，最初提议额外维护一个持久的“需要恢复”集合。

用户指出：

> 这样复杂度会非常高

agent 撤回第二套持久索引，改为提议在 JSONL 末尾新增 `SessionParked` event，供启动时判断是否需要恢复。

用户否决该新增 event，并给出选择：

> 不需要，明确结束的 session 是很明显的，结尾就是个 end，其它情况检查一遍又能怎么样，不如按时间倒序来恢复，只要速度够快，支持 10w 个 session，就不是什么大问题，只是需要注意不要全 load 到内存，一个一个或者一批一批来

### 已确认决策

> 不增加持久恢复集合，也不增加 `SessionParked` event。进程启动时扫描已有 session；结尾是完整 `end` 的 session 明确无需恢复，其他 session 逐一检查并根据持久状态决定是否恢复。
>
> 恢复按最近活动时间倒序进行，使最近使用的 session 优先恢复。扫描和恢复必须流式或使用有界批次；同一时间只加载一个或有限数量 session 的完整历史和领域 state。所有 session 的轻量内存状态由第 104 项单独确定。
>
> 启动恢复需要用十万级 session 做性能验证。目标是让全量检查本身足够快，而不是为避免检查引入第二套持久状态。

时间排序只决定恢复优先级，不决定是否恢复，也不是会话事实来源。

## 104. 启动恢复期间立即提供服务，并为所有 session 保留轻量槽位

### 校对对话过程

用户补充启动恢复与内存生命周期设计：

> 提供服务，有请求的 session 优先执行检查，并且不重复检查同一个 session，内存里会有整个历史所有 session 的状态，如果是正常结束的，就一个 bool 值就行了，如果需要恢复或者 active，就有runner

agent 的理解是：服务不等待全量恢复检查结束；所有历史 session 在内存中都有轻量槽位，但只有需要恢复或正在活动的 session 才持有 runner 和完整领域 state。同一槽位同时协调后台检查和请求触发的优先检查，保证两者不会重复检查同一个 session。

### 已确认决策

> zork-agent 在后台恢复检查尚未完成时就提供服务。对尚未完成检查的 session 收到请求时，该 session 的检查优先于后台顺序执行；请求与后台扫描必须汇合到同一次检查，不能并发或先后重复检查同一个 session。
>
> 内存中为全部历史 session 保留一个轻量槽位。正常结束且当前没有工作的 session 只保留布尔状态，不保留 fold 后的完整领域 state，也不保留 runner。
>
> 需要恢复或当前 active 的 session 在槽位中持有唯一 runner；完整领域 state 只随这些 runner 存在。runner 正常结束并退出后，槽位退回轻量布尔状态。

第 103 项的“有界加载”限制针对 session 历史和完整领域 state，不禁止在内存中保存十万个 session ID 及其轻量状态。

### 已确认决策

默认上下文处理方式为 compaction，handoff 保留，可按 session 配置无缝替换。前置检查选择 step；普通 step 不感知策略，交接 step 准备好后统一提交新 generation，复用现有 ModelGateway、step 生命周期、持久化和恢复路径，不增加策略执行框架。

compaction 使用当前模型和 thinking 独立生成摘要，材料为前次文档与被移出的旧前缀，不提供工具；保留可配置的最近原文，默认目标 20,000 个估计 token。按完整调用/结果组切分，允许在单个超长 turn 内切分。handoff 保持 user role 完整用法、固定 call schema、只提交 document 的协议。

两种方式共用文档验证结果后的提交、snapshot、旧 provider continuation 释放和无文档兜底。文档生成失败不能使 turn 卡死；有限次文档尝试耗尽或交接上下文被明确拒绝后，无文档进入新 generation 并继续同一 turn。只有文档可以缺失，原始历史、未消费输入、未完成工具、未交付结果、tool state 和 session 配置正常保留，并提供历史恢复指引。普通网络、鉴权、限流故障仍遵守原有独立 provider 重试规则。

摘要请求的真实 usage 必须计入总消耗，但不作为主对话 token anchor；摘要文字和流式输出不伪装成普通助手回复。主对话继续使用 API 返回的准确 input token 数及其后的增量估计。

### 对前文的修订

第 56—59、92、101 项涉及 generation 切换的共同规则，现在同时适用于 compaction 与 handoff。持久提交使用中性的 `ContextApplied` / `ContextFailed`；旧 handoff 文档协议本身保留。配置变化只影响下一次交接，不改变已开始操作的 purpose 和原文保留边界。

摘要材料必须有界，避免为摘要复制巨大工具结果；默认采用工具输出摘录、前次文档更新及最近原文保留，参考 [pi 的 compaction 实现](https://github.com/earendil-works/pi/blob/4e69b0c28060f0f02fbe38bfa7c21a2e2eb25057/packages/coding-agent/src/core/compaction/compaction.ts)。具体实现、字段和验收合同见结构化规范第 7 节。
