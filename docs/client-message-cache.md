# 客户端消息缓存

已投递消息由 Rust core 按条存入 `ClientStore`，不再将当前视图的整份消息列表序列化为一个缓存值。桌面 `Conversation`、移动端订阅和移动端离线读取使用同一份数据。

## 数据与查询

- `delivered_messages` 以 `(node, session, id)` 去重。重复消息不改写已存正文，不改变顺序。
- `(node, session, position)` 唯一索引支持最新页和向前分页；每次默认读取 100 条，使用位置游标，不使用 `OFFSET`。位置只表达本地已缓存范围内的 Station 消息顺序，不是同步协议的版本号，也不按消息 ID 或客户端时间排序。
- `message_history` 保存已缓存连续范围之前的 Station 游标。历史页面和范围边界在同一事务提交；本地还有更早消息时返回 `zork-cache:` 游标，仅 core 消费，不发送给 Station。
- 新消息追加到范围尾部，历史页扩展范围头部。实时连接仍先订阅、再按最后一条已确认消息追赶；手动刷新也追赶到该锚点，避免仅合并最新 100 条留下缺口。页面不能凭空填造内部顺序；检测到内部缺口时回滚并报告错误。
- 旧 `messages:{session}` 和 HTTP 消息快照按聊天首次读取时事务迁移。可识别的 outbox 待发送行不进入已投递历史；迁移失败保留原值。

消息库只接收服务端页面与消息事件。乐观显示、待发送和失败重试继续由 outbox 管理，不以乐观消息 ID 作为追赶锚点。撤权时清除对应设备的消息与范围；旧绑定的在途写入不能重新填回撤销的数据。

## 会话生命周期

`Device` 保留最近使用的至多 8 个会话，并对这些会话的消息内容与行结构设置合计约 32 MiB 的保留预算。它们在页面切走后仍可接收消息，切回时复用已有状态和连接。预算是消息数据的估计值，不是整个进程的硬内存上限。

超出预算按最近访问顺序淘汰 core 的强引用。外部仍持有的活动会话继续有效；无外部持有者的会话随之取消 IO。淘汰不删除已入库历史，再次打开先读本地最新一页，再追赶服务端。未保留的聊天不会仅因其历史在库中而永久维持实时连接。

## 验证

```sh
eval "$(python3 scripts/lib/build_env.py --shell)"
cargo test --locked -p zork-client-core
cargo bench --locked -p zork-client-core --bench messages --no-run
```

编译完成后单独运行 Cargo 输出的 benchmark 可执行文件，避免与构建、GUI 压测争抢资源。`messages` 基准固定写入单聊天 1,000,000 条和 100 个聊天合计 1,000,000 条，校验真实记录数与索引执行计划；测量最新、历史中部与起始页、跨聊天查询、重新打开 SQLite 连接、重复页面、单条追加及后台追加期间的查询延迟。样本包含正文、Markdown、代码、批注、附件和长内容。

报告同时比较旧整 JSON 快照的读写成本。普通查询采用 500 个样本；昂贵的旧快照只有 10 个样本，其 p95/p99 仅表示这组样本的最大值。重开连接不清除操作系统文件缓存，不能当作冷磁盘测试；该基准不测原生窗口 FPS。临时数据库在退出时删除。
