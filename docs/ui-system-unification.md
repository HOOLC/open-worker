# Zork UI 整体统一方案

状态：已开始实施。以 [现有设计规范](gui-approved-design.md) 为主入口；本文记录批次、范围和完成证据，不另建一套视觉基线。
交互细则见 [ui-interaction-states.md](ui-interaction-states.md)。

## 统一目标

同一种信息有一致的视觉层级，同一种操作有一致的行为，新增页面可以自然复用这些约定。
保留当前暖灰背景、白色内容、炭墨文字、动物头像、柔和圆角与轻量动效。
覆盖 Zork 自有的桌面、Web 对照和 Android 界面；内嵌浏览器的网页内容及系统授权界面遵循各自来源。

## 现状与基础

- `zork-ui` 已包含颜色和布局定义、控件、弹窗、导航、消息、附件、状态提示和动效；PC 与 Web 可以复用同一份 Rust 实现。
- 当前定义分布于 `design.rs`、`controls.rs`、各组件与应用视图；同类样式仍有页面自定义。
- `controls.rs` 同时承载许多基础控件。迁移时按职责逐步拆分，保留调用适配，避免仅改目录却保留重复配方。
- Android 已有 `Theme.kt`、`SettingsControls.kt` 等基础，颜色与 PC 仍是分别维护。例如当前危险色并不相同，需要明确统一或登记理由。
- 当前图库可展示基础组件和部分组合页面。它需要成为完整状态和真实页面的持续对照入口。

## 四层结构

| 层 | 负责什么 | 调用者提供什么 |
| --- | --- | --- |
| 设计定义 | 语义颜色、文字层级、间距、轮廓、尺寸、动效与层级关系 | 语义角色和平台／尺寸变体 |
| 基础组件 | Button、IconButton、ActionLink、Field、Select、Switch、Badge、Avatar、Surface 等 | 内容、状态、事件、可访问名称 |
| 组合组件 | PageHeader、Section、FormField、SettingsRow、Menu、Dialog、EmptyState、MessageRow 等 | 业务展示数据和标准操作插槽 |
| 页面 | 数据、路由、业务权限、操作结果、组合与响应式安排 | 使用前三层，不重新决定常规状态外观 |

在现有 GPUI／Compose 之上建立薄的语义入口，避免再实现一套底层布局或事件系统。
组件保留清晰的内容与操作插槽；只有出现真实重复需求时才增加变体，不以无限参数覆盖每个页面的特例。

## 统一范围

### 颜色与材质

定义 canvas、subtle surface、raised surface、body text、secondary text、border、selection、interaction、success、warning、danger 等语义。
交互色与背景色分开命名，组件不用“侧栏色”表达全局 hover。
成功、在线、待验证、失败等状态的颜色含义固定；配合文字或图标，不能只依赖颜色。
卡片、菜单、弹窗按浮层层级使用边框、阴影与遮罩配方，不在每个页面另选透明度。

### 文字与密度

收敛为页面标题、分区标题、正文、控件标签、辅助说明、元信息、代码等少量文字样式。
每个样式同时定义字号、字重、行高和默认颜色；页面选择用途，不分别拼四个参数。
默认与紧凑密度共同定义控件高度、内边距、图标和间距；不只把高度压小。
遵循现有客户端字号设置、系统无障碍字号与中英文换行规则。

### 形状、间距与资源

保留胶囊按钮、圆角输入框、卡片和弹窗的既有家族，尺寸和轮廓由家族决定。
组件内部间距、组内间距、分区间距、页面边距分别给定预设；边框和图标允许细粒度数值，不机械把所有几何变成同一倍数。
普通操作统一图标来源、视觉大小与描边；提供商标识、品牌和动物头像保留各自资源规则。
头像的身份来源和缺省规则同样归共享展示逻辑，避免列表与聊天在同一 Agent 上显示不同默认图。

### 完整交互

所有适用组件覆盖 default、hover、pressed、selected、focus-visible、disabled、busy、invalid。
同时定义键盘激活、焦点顺序、关闭与返回、点击范围、嵌套操作、动画中断与减少动态效果。
组件负责禁用、忙碌的基础反馈和交互契约；业务授权校验仍由业务层负责。
公开接口的行为说明与实际演示一致，例如静态状态样本不能冒充真实键盘操作验证。

### 页面结构

设置页统一内容列、标题与主操作位置、分区间距、字段说明、保存与错误反馈。
列表统一行的 leading／content／trailing 结构，以及整行操作与独立按钮的关系。
弹窗统一标题、关闭、内容滚动、页脚、加载／错误位置、焦点恢复与 Esc。
空态、首次加载、后台刷新、加载失败、局部提交失败使用一致的反馈位置，保留原内容与用户输入。
聊天、任务、历史、文件等复杂页面使用专用组合组件，保持已有阅读锚点、选择、草稿、虚拟列表和更新边界。

## 跨端边界

- PC 与 Web：共享 Rust 组件与状态配方，分别验证实际渲染和输入。
- Android：共享语义颜色、资源与状态含义；使用 Compose 控件实现，并保留至少 44dp 独立触摸区及已有 48dp 行操作规则。
- 手机保留底部表单、系统返回、IME 与触屏反馈；PC 保留指针、键盘、tooltip 和适合桌面的布局。
- 首先形成 token 对照清单。对已稳定、确实相同的颜色和字体角色建立单一可生成定义，输出 Rust／Kotlin；平台几何与原生行为分别配置。
- 不把现有不同值直接全部覆盖：逐项判断是有意的平台差异，还是重复维护的偏差。

## 迁移批次与完成条件

| 批次 | 内容 | 第一批代表页面 | 完成条件 |
| --- | --- | --- | --- |
| 1 基础操作与表单 | 按钮、图标操作、文本操作、输入框、选择器、开关；补齐状态 | 模型设置、聊天工具栏 | 真实状态对照通过，相关入口都使用共享实现 |
| 2 行与信息组织 | 导航行、菜单项、设置行、状态标签、头像、分隔和密度 | 设备／Agent 导航、模型列表、附件列表 | 选中与 hover 组合、长文案、嵌套点击一致 |
| 3 浮层与反馈 | 菜单、tooltip、弹窗、底部表单、空态、忙碌和错误 | 模型编辑、全文阅读、文件预览 | 滚动与页脚、焦点恢复、关闭和失败恢复一致 |
| 4 复杂组合与整页 | 聊天消息、历史、文件、Composer；页面标题、内容列、分区 | 聊天、任务、历史、设置 | 页面结构一致，已有交互与性能没有退化 |
| 5 收尾与跨端 | Android 对齐、删除过渡适配、梳理剩余直接样式 | 同类 PC／手机流程对照 | 覆盖清单闭合，例外有用途和归属 |

每批都先在图库展示真实组件的完整状态，再落入代表页面核对，随后迁移这一家族的其余调用点。
Android 在每批同步校对语义，最后一批集中处理残余差异；不等 PC 全部完成才发现跨端定义不兼容。
记录“现有实现 → 目标组件 → 调用点 → 已验证状态／平台”，以此判断是否完成；替换了部分截图不代表整个家族完成。

## 如何防止再次分叉

- 新页面优先使用现有语义组件。确需新增变体时，先更新共享实现和状态示例，再用于页面。
- 组件示例同时是使用说明：展示长标题、中文、错误、禁用、忙碌、键盘和紧凑宽度，而非只有漂亮的默认状态。
- 规则检查关注新增的业务层原始交互色、常规圆角配方和重复控件，允许具名特殊画布、品牌动画、数据可视化和第三方内容例外。
- 过渡适配器标记使用方与删除条件，相关调用点完成迁移后删除，不长期保留新旧两套默认入口。
- 高频组件验证静止不持续刷新、状态切换不重新解析内容、长列表只构造可见行；按受影响模块使用现有性能验收，不以静态截图代替。
- 每次交付提供同条件的组件／页面前后对照，标明平台、窗口尺寸、实际运行的检查和尚未覆盖的范围。

## 下一步建议

将已认可的按钮反馈作为基础，在同一页补齐文本操作、输入框、下拉、开关和状态提示；随后用“模型设置页”验证一次完整的组合效果。
这能同时检验组件本身、页面密度、文字层级和反馈位置，再据此推进其他页面。
