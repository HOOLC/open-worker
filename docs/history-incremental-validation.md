# History 增量聚合与验证

2026-09-11。对应[当前订阅合同](client-state-subscriptions.md)。此次优化执行历史的 core 聚合与增量传递；没有改变历史条目的业务含义、页面排版或网络分页协议。

Session 执行历史存储在执行节点。这里的索引、已加载记录和聚合结果都只在 Rust core 内存中，不新增客户端数据库表、历史文件或磁盘索引；UI 消费只读结果。“首次载入”测的是记录到达后的内存初始化，不是从客户端数据库读回历史。

本报告记录的是执行详情已到达 core 后的匹配/增量测试与性能基线。随后 Session 概览改为 SSE snapshot 加后续提交，统计与 hover 不再调用此详情加载路径；下面的十万条物化数字不代表打开会话或概览的成本。该协议的验证另见[Session snapshot 验证](session-snapshot-validation.md)。

## 实现

`History` 的写侧状态持有唯一的增量 ledger。新页先按事件 ID 去重，再将不可变记录共享给按步骤/调用 ID 建立的证据索引；只重新整理受影响条目的证据。原来的每页全量 `entries_iter`、排序和 `HistoryChange::reconcile` 已从生产更新路径移除。完整快照 helper 也使用同一 reducer，旧实现仅保留在差分测试中。

模型选择按事件顺序索引。补载早期选择只影响第一条已知选择之前的步骤；一页含多个选择时先完成整页索引，再处理一次依赖区间。`wait` 根据后续的同调用截止事件、消费输入的步骤开始、轮次结束或下一次等待确定结束状态，支持结果先于调用记录到达。

条目顺序由实测时间与首次出现位置共同确定，保留同时间条目的稳定顺序。事件位置在前插时不重编号；写侧有序索引和只读条目列表使用持久序列。相邻的新条目整段插入，移动和远距离修改产生有序 edits。小尾部追加、前插和等长替换直接更新序列块，避免单条修改也触发完整的 RRB 拼接。

## 性能

同一主机与 release 配置，加载 1,000 / 10,000 / 100,000 条执行记录，1 / 8 个订阅者，每个场景 100 次采样。输入包含模型选择、步骤开始/完成、工具参数与结果、用户输入、等待/唤醒、用量和长正文。先完成编译，再单独运行固定二进制；测量时未运行其他 Cargo/rustc/Java 构建。

十万条记录、8 个订阅者，**core 提交加全部原生订阅者应用**的合计耗时：

| 操作 | 改造前 p95 | 改造后 p95 | 改造后 p99 |
| --- | ---: | ---: | ---: |
| 追加一条 | 127.061 ms | 6.375 µs | 12.458 µs |
| 完成早期步骤 | 123.035 ms | 13.167 µs | 25.583 µs |
| 前插 100 条 | 146.462 ms | 238.792 µs | 275.458 µs |
| 重复相同事件 | 0.458 µs | 0.583 µs | 0.958 µs |

单独的 core 提交 p95 分别为 4.917 / 8.292 / 148.166 / 0.166 µs。追加和早期步骤完成每次每个订阅者只应用一条记录；补载应用 100 条，重复输入不产生 edits。重复输入原本已能去重，因此没有宣称该项获得性能提升。

追加一条的 core 提交 p95，在 1,000 / 10,000 / 100,000 条、8 个订阅者下分别为 2.708 / 2.333 / 4.917 µs。该路径已不再与全部历史正文量线性增长。前插 100 条分别为 152.167 / 105.792 / 148.166 µs。小样本存在进程预热和主机调度差异，保留全部分布，不从微秒数推导设备 FPS。

分配在单独的 System allocator 计数二进制中测量，避免影响前后耗时对比。十万条、8 个订阅者的单次追加，p95 为 93 次分配调用（含 realloc）、15,517 字节分配请求、8,257 字节额外存活峰值；1,000 条时对应分配请求为 14,661 字节。输入 JSON 的构造在测量区间外；测量包含 core 接收记录、投影、发布和原生 patch 应用。

首次一次性载入十万条仍需处理全部数据并构造内存索引。本次每组各一次的冷载入样本从 109–131 ms 增至 192–201 ms；这是当前实现初始化这些数据结构的整体成本，不是 p95 结果，也不是增量方案必须付出的固定代价。正常生产分页每次请求 100 条，此处特意测量一次性加载的极端情况。新实现十万条混合 fixture 的持有堆约 470 MiB，包含原始记录、条目正文及全部索引；该数值不是订阅日志大小，也不是进程 RSS，未测改造前同口径堆占用。

## 正确性与检查

- 与改造前全量实现做差分对照：12 组确定性事件序列，各 400 条，随机交替补载旧页和追加新页；覆盖同名并发调用、重复步骤 ID、乱序完成、时间相同/缺失、模型切换、等待被唤醒/中断及迟到截止事件。
- 十万条 ledger 回归确认单条追加和远距离完成只涉及各自条目；旧页里的空模型选择不会无故重建整段已有条目。真正新增的早期模型选择仍正确更新所有受影响步骤。
- core 从中间页开始，交替加载两侧并注入重复页，验证排序、列表 edits 和完整投影一致；慢消费者取消 prepared 后可重放，积压 600 次提交后 Reset 与快消费者收敛。
- 10,000 条历史的两个远距离更新只传递两个 edits，未修改条目保持共享；撤权使在途批次失效并清除记录与索引。仅 runtime 改动不修改历史行。
- 持久列表的小 splice 与独立 `Vec` 模型比较，覆盖十万条、600 次首部/尾部/中间操作及块边界；旧快照保持不变。
- `cargo test --locked -p zork-client-types -p zork-client-core -p zork-observe` 通过：core 78 单测、16 集成测试；types 24 单测；observe 6 单测、10 协议测试。需独立 Station 的 enrollment 用例按原配置忽略。
- 桌面 `headless_history` 在 1280×800、900×600 通过，涵盖条目、折叠、时间轴、实时来源、时钟和静止指针下的滚轮交互；`zork-ui` 的 7 个相关历史回归通过。
- 修改后的 `zork-client-types` 与 `zork-observe` 编译到 `wasm32-unknown-unknown` 通过；此项验证公共库的目标平台兼容性，没有重建完整 Web 展台。
- 客户端边界、Rust 文件格式、diff 空白和文档链接检查通过。全部测量结束后核对源码摘要仍一致。

## 重现与证据

```sh
python3 scripts/lib/build_env.py -- env CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0 CARGO_BUILD_JOBS=4 cargo bench --locked -p zork-client-core --features headless-bench --bench history --bench subscriptions_alloc --no-run
```

构建完成后，在没有其他编译或负载测试时，分别执行 Cargo 打印的 `history` 路径和 `subscriptions_alloc` 路径（后者传 `--history`），stdout 保存为 JSON。两个二进制分别负责耗时和分配；不要并行执行测量。

本地验收产物：

- 改造前分布（本地生成的验收记录）
- 最终分布（本地生成的验收记录）
- 分配与持有堆（本地生成的验收记录）
- 源码与二进制摘要（本地生成的验收记录）
- 仅替换 ledger 后的中间结果（本地生成的验收记录）：当时逐条拼接持久序列导致前插 100 条仍约 9 ms，随后通过整段插入与小 splice 路径消除，没有减少原负载。

本次未测 JNI、Compose、网络 IO、UI 分组和时间轴布局，也未测实际屏幕 FPS。历史首次物化和真正受影响的大范围条目仍需要相应工作；一个条目累积很多事件时，会重新整理该条目的证据。当时 UI 的分组、用量汇总及时间轴布局仍有独立的全量计算（用量汇总随后已迁至 Session snapshot），不能把此次 core 数字当作整页呈现耗时。
