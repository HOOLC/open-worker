# 同步空闲合同

同步请求使用 POST 承载游标与分页参数，不代表业务修改。HTTP 中间件不得依据方法或路径生成数据变更通知。

## 提交与通知

业务投影 `sync_entities` 与 `sync_meta.sequence` 在同一个 SQLite 事务中更新；值相同不推进版本。SQLite 列级触发器只在 sequence/epoch 真正变化时更新 `sync_change_signal`，提交 hook 再将它转成同步唤醒；floor 维护不触发该标记。回滚不通知。导出缓存、分页位置和命令回执等 `sync_*` 内部记账不产生工作或客户端变更通知。

SSE 的 `catalog` 携带 owner、epoch、scope、sequence。它是追赶提示，实际数据仍通过分页协议落盘。旧客户端继续使用领域 revision；新客户端用持久游标忽略已覆盖的提示，不比较不同 owner/epoch/scope 的 sequence。

## 文件权威与查询

Profile、设备配置和升级状态由独立后台协调任务投影到 SQLite。任务先订阅内核文件变化，再读取；父目录通知负责原子替换与目录重建，只有读取或注册失败才按上限 30 秒退避恢复。相同投影不写入、不产生版本。初始化尚未完成时同步请求有界等待，失败保留旧投影。健康协调没有周期性查询。

同步拉取只读取业务投影；冻结导出页所需的内部缓存写入不改变业务版本。保留窗口维护在后台执行。

## 客户端收敛

设备事件处理顺序执行追赶。一次拉取覆盖的重复或较旧提示直接忽略；拉取期间出现更高版本，随后继续追赶。通知可合并；流溢出发出 resync，重连通过持久化游标补齐。未满足的同步需求在失败后重试，成功后不再周期性全量校验。此优化不改变未确认命令的重放规则。

已投递聊天消息按条增量缓存，重复页面不写库；本地分页和会话保留策略见[客户端消息缓存](client-message-cache.md)。消息位置与 catalog 的持久化同步版本分别管理。

消息到达 activity 由共享 core 按会话发布，与历史投影及 Agent 运行状态分开。历史恢复、分页、重连追赶和重复回执不产生到达事件；实时投递及新加入的本地待发送消息在去重后推进 activity 序号。订阅者从订阅时的序号开始，合并更新保留新增总数和最多 32 条动画消息 ID。桌面与 Android 只消费这个增量驱动入场、尾部跟随和新消息提示，不通过比较历史末条消息或连接状态推断到达。

## 回归

- `cargo test --locked -p zork-gateway db::sync`：空读、重复协调、回滚、真实修改，以及客户端重复提示收敛。
- 先构建 `zork-gateway`，再执行 `python3 scripts/test-sync-idle.py`：真实 HTTP/SSE 读取与改名闭环。可用 `ZORK_TEST_BIN_DIR` 指向本轮构建目录。

合同是无新业务变化时同步链路停止业务查询；心跳不读取业务状态，失败退避和保留窗口维护各自独立。统一接入方式见 [Mesh 订阅与通知基建](mesh-notifications.md)。CPU 百分比需要在实际交付设备上单独复测。
