---
name: skill-management
description: Create, improve, archive or troubleshoot Zork skills and manage the current agent's skill source directories.
---

Use `skill.sources` to inspect the shared, device and current-agent sources. Use `skill.list` to inspect available skill files and loading diagnostics. Choose an existing skill by its listed path and read it with `file.read` before changing it. Continue from `next_offset` until the whole document is read. These tools use the normal `call` / `tool.help` protocol; request help for exact current schemas.

Choose the scope from the user's request. Reusable instructions belong in the shared source; device-specific commands and environment assumptions belong in a device directory; agent-specific workflows belong in an extra source for that agent. A shared filesystem path is not automatically appropriate for every device. Do not put device folders beneath the default shared skill root, since discovery is recursive.

`skill.sources` with `action: "add"` or `"remove"` changes only this agent's extra sources. Use the exact configured path returned by the tool when removing one. Adding a source does not copy or install files; removing a source does not delete its skills. Node defaults remain managed by node configuration. If this session has no owning Agent, source editing is unavailable; report that distinction rather than claiming a successful change.

Source roots must already exist. Create a missing local source directory with shell.run when that is part of the requested work; if a shared mount is unavailable, restore the mount instead of creating a local substitute.

For a new skill, choose an explicitly returned source and a relative directory such as `review-code`. Use `skill.write` with `source`, `directory`, and the complete `content`. Omit `expected_hash` only when creating a new manifest. For an update, run `skill.validate` on the complete text you just read and use its `content_hash` as `expected_hash`. A conflict means the file changed: re-read it, preserve the concurrent changes and revise the update. Do not retry by dropping the hash.

A skill needs `---` frontmatter with `name` and `description`, followed by useful instructions. Prefer a short lowercase hyphenated name. Make the description state when the skill applies. Capture reusable decisions, actual constraints and non-obvious procedures; keep temporary progress, credentials and incidental machine details out of shared skills. Respect the user's existing authorization and scope; do not invent approval requirements. Explain relative references from the skill's directory. Use existing `file.write` / `file.edit` for supporting resources and validate any scripts that you add. `skill.write` changes only SKILL.md and preserves those resources.

Use `skill.validate` to check a draft without writing. It checks the supported frontmatter, content and size, not factual correctness or script behavior. The supported frontmatter is a string subset: plain strings, JSON-style double quotes, YAML single quotes and indented `|` / `>` descriptions; other metadata is ignored. No YAML anchors, tags or multiline quoted strings.

To retire a skill, use `skill.archive` with its explicit source, directory and current `expected_hash`. It retains the manifest in a hidden archive and leaves resources in place. Other same-name files remain separate candidates; check the returned catalog. Restore by reading the returned archived file and creating the active manifest with `skill.write`.

After a mutation, inspect the returned catalog or call `skill.list` and verify the intended file path and metadata. Same-name skills are all retained; names do not establish identity or priority. Choose by task, device, description and source; read multiple candidates when needed and ask the user only if the ambiguity remains material. Fix loading diagnostics. Changes are discovered before the next normal model request; there is no restart or installation step. Release-provided skills are ordinary files selected from `bundled-skills/.versions/`. Their source directories are release-managed: do not edit or archive them in place. To customize, copy the whole skill directory (including resources) into `custom-skills/` or another suitable configured source, make the copy owner-writable, and edit that copy. If it replaces the built-in workflow, disable the bundled skill after verifying the copy. Use `skill.sources` to find destination paths; same-name copies remain distinct candidates.

Use `skill.bundle` for node-wide distribution management. `action: "list"` shows the active version, saved complete versions and disabled skill IDs. `disable` / `enable` with `skill` change visibility for all agents on this node without deleting the files. Use the stable directory ID from the listing, not the frontmatter name. These choices survive updates and rollback. `rollback` with a listed `version` selects that entire saved release, including resources; it leaves custom copies alone. Rollback persists across restarts while the application's shipped skill revision stays the same; a different shipped revision resumes normal updates.

On upgrade, release files are replaced by a complete new version, selected atomically. Custom files are independent and are not backed up, merged or migrated by the updater. Previous complete releases stay available for rollback. Integrity checks reject incomplete or damaged release versions; they do not create local-edit copies.
